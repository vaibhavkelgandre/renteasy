# 5. Design system

**Read this before writing any new markup.** Everything here exists so the tenth page needs no new
decisions.

Tailwind **v4**. Tokens live in `client/src/index.css`'s `@theme` block — **there is no
`tailwind.config.js` and no `postcss.config.js`**, which is the v4 way and will send you looking for
both if you follow a v3 tutorial.

---

## 1. Identity: teal on warm stone

| | Choice | Why |
|---|---|---|
| Neutral | **stone** | A *warm* grey. On a page where a stranger decides whether to lend you an ₹80,000 camera, warm neutrals read as friendly and cool ones read as administrative |
| Primary | **teal** (`--color-brand-*`) | Trust and availability, without emerald's "success message" connotation or blue's corporate-software feel — and distinct from the two colours that dominate this space, Airbnb's coral and every booking site's blue |
| Destructive | **rose**, only | The single red, so red always means "cannot be undone" |

`bg-stone-50`, not white: a page of white cards on white has no structure, and a faintly warm ground
gives every card an edge without borders everywhere.

## 2. Type

**System font stack, no webfonts.** A marketplace is found on a phone on mobile data, and a download
either blocks first paint or reflows visibly when it lands.

**16px base, deliberately not 14px.** An internal tool optimises for density because people live in
it; a consumer marketplace optimises for comfort because people arrive once and must not squint.

**`font-mono` + `.tabular` for prices and rental periods.** Money is the thing people compare here —
₹800/day against ₹15,000/month — and comparison needs digits that line up. Tabular figures make a
column of prices scannable instead of ragged.

## 3. Layout

**A light, translucent header — not a dark app bar.** A dark bar says "you are inside a system"; a
marketplace should feel like a shop window, with the chrome out of the way of the things being
rented.

**It renders for signed-out visitors too**, because browsing needs no account. That is why
`AppLayout` must not assume a user, and why `Header` and `VerifyBanner` each handle the absent case
themselves.

**`AppLayout` owns the page width** (`max-w-6xl`, narrower than an admin tool's) — no page sets its
own, or the layout appears to shift as you navigate.

## 4. The primitives

`client/src/components/ui/`. **Check here before writing markup** — the second hand-made button is
where drift starts.

| Component | Notes |
|---|---|
| `Button` | `variant`, `size`, `loading`, `fullWidth`, `as`. **`loading` implies disabled** — separating them is how a form gets submitted twice. `as={Link}` keeps a navigation a real link, so middle-click still works |
| `Field` | Bundles the label via `useId`. Marks what is **optional** rather than what is required — asterisks on every field of a signup form are noise, and people abandon forms that look longer than they are |
| `Checkbox` | `size-5`, not the browser's ~13px. The control carrying a legal agreement should not be the hardest thing on the page to hit |
| `Card` | Rounded generously, soft shadow — reads as a product tile, where a thin border reads as a data table |
| `Alert` | **Never a toast.** A toast disappears on a timer, which is exactly wrong for "check your inbox" — the reader looks away and the only instruction is gone |
| `Logo` | Inline SVG: an `<img>` costs a request and a flash of nothing |

**Sizes:** `md` is `h-12` (48px), taller than an internal tool's control. Used one-handed on a phone,
comfort beats compactness.

## 5. Rules that are easy to break by accident

**Copy that must stay true in several cases at once.** `CheckEmailPage` is the example: the API
answers identically for a new, unverified and verified address, so *"account created"* and *"we've
sent you a link"* are both **false in at least one case**. The wording has to be true in all three
and distinguish none — and there is a test asserting the rendered page contains none of the tempting
phrasings. It is genuinely easy to "improve" that copy into an enumeration oracle.

**A failure the API refuses to explain must not be explained here either.** `VerifyPage` shows one
message for expired, used, unknown and malformed tokens, because the API does. The copy is about
**what to do next**, which is the only useful thing to say when the cause is deliberately withheld.

**Nag, don't block.** `VerifyBanner` sits above the content for an unverified user. Blocking them
from browsing would hide the very thing that makes confirming worth doing; the refusal belongs at the
moment they try to list or book, where the reason is obvious.

**Mirror the server's single answer.** After a resend, the UI says "check your inbox" whatever
happened — sent, cooldown, already verified. Inventing a distinction the server refuses to make is
how the client becomes the leak.

**Status is words plus an indicator, never colour alone.**

**No mocked data.** `HomePage` has no fake listings: a placeholder tile reading "Canon EOS R6 —
₹800/day" is indistinguishable from a real one, and a page of invented inventory teaches you to
distrust the real listings when they arrive.

**A disabled control needs a reason.** The register button is disabled until the terms version loads
— the server refuses a stale version, so a button that could only fail is worse than one that waits.

## 6. Accessibility, as implemented

Not a checklist — the specific things the code does, so a new component can match:

- `Field` / `Checkbox` associate every label via `useId`, set `aria-invalid`, and link the message
  with `aria-describedby` so it is announced on focus.
- `Alert` uses `role="alert"` + `aria-live="assertive"` for errors, `role="status"` + `polite`
  otherwise.
- `Button` sets `aria-busy` while loading — the spinner is visual only.
- Loading states announce themselves in an `sr-only` `role="status"`; a pulsing logo tells a screen
  reader nothing.

**The tests assert these**, querying by label and by role — so a field that loses its label
association fails a test rather than shipping.

## 7. Deferred

**React Query** — declared in the stack, unused. It earns its place on data that is fetched, cached,
paginated and invalidated: listing grids, search results. A session is one object fetched once, and
`AuthContext` is less machinery for the same result. **Introduce it with the first real list** (step
5), not before.

**Dark mode** — not built. Would double every colour decision above. Revisit only if asked.
