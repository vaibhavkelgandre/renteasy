# 7. Functional requirements — the complete list

**Every requirement in the product, built or not.** This is the canonical list and the only one —
[`1.status.md`](1.status.md) points here rather than keeping its own copy, because two lists of
requirements always drift.

**Status:** ✅ built & tested · 🟡 partly built · ⚠️ code exists but **nothing uses it** · ⬜ not started

Last updated: **10 September 2026** · **149 requirements** — 71 built · 11 partial · 1 unwired · 66 not started

## How to use this

Cite the ID. `FR-103` means exactly one thing and will keep meaning it.

> *"Build FR-100 to FR-107 — listing create, rate card and publish."*
> *"FR-401's breakdown isn't itemised. Fix it."*
> *"What's blocking FR-500?"*

**IDs are never reused and never renumbered**, including if a requirement is dropped — a dead ID is
marked withdrawn and left in place, because a renumber silently invalidates every note and commit
message that referenced the old number.

Ranges are sparse on purpose, so a new requirement slots in beside its relatives instead of landing
at the end.

Spec: [`features/02-password-reset.md`](features/02-password-reset.md)

Hit as a real wall in development: an account's password was lost and the only recovery was deleting
the row.

| ID | Requirement | Status |
|---|---|---|
| FR-020 | Request a reset by email address | ✅ |
| FR-021 | **The response never reveals whether the address is registered** — same rule as FR-006 | ✅ |
| FR-022 | Single-use token, short expiry (1h), stored only as a hash | ✅ |
| FR-023 | Resend cooldown (15 min), returning silently when too soon | ✅ |
| FR-024 | A used, expired or unknown token answers **byte-identically** | ✅ |

> **A reset does not sign out other sessions**, and that is the significant remaining gap in this
> area — a JWT is signed over the user id, not the password hash, so a session stolen before the

> [`1.status.md`](1.status.md) §8, not as an FR yet.
>
> **There is no "your password was changed" notification.** Standard practice, and the thing that
> tells a real owner their account was taken. Deliberately not built: nothing in FR-020–027 asks
> for it, and it should arrive as its own requirement rather than as a surprise.

## Listings & rate card — step 3 ✅

Spec: [`features/04-listings.md`](features/04-listings.md) · Media: [`6.media-storage.md`](6.media-storage.md)

| ID | Requirement | Status |
|---|---|---|
| FR-100 | Create a listing as a **draft** — not visible to anyone else | ✅ |
| FR-101 | Required: title, description, category, condition | ✅ |
| FR-102 | Category from a fixed set (camera, bike, tool, appliance…) — a **lookup table**, not a CHECK | ✅ |
| FR-103 | **Rate card: hourly, daily and monthly prices — at least one required**, integer paise | ✅ |
| FR-104 | Security deposit amount, integer paise, may be zero | ✅ |
| FR-105 | 1–8 photos, 5MB each, real type sniffed, **EXIF stripped** | ✅ |
| FR-106 | Photo ordering; position 0 is the cover shown in the grid | ✅ |
| FR-107 | **Publish requires: a verified email, ≥1 photo, ≥1 rate, and a location** | ✅ |
| FR-108 | Edit any field while draft or published | ✅ |
| FR-109 | Unpublish — hides it from browse, keeps confirmed bookings intact | ✅ — both halves, and the second is now tested |
| FR-110 | Delete only when no active or upcoming booking exists | ✅ — **stricter than asked**, see below |
| FR-111 | **Only the owner may edit, unpublish or delete** — a relationship check, not a role | ✅ |
| FR-112 | **Changing the rate card never alters an already-confirmed booking** | ⬜ — belongs to bookings, see below |
| FR-113 | Location is an **area** (locality + city), never a street address | ✅ |
| FR-114 | Minimum and maximum rental duration per listing | ✅ — stored and validated; **enforced against a request at step 6** |
| FR-115 | Owner sees their own listings, drafts included | ✅ |
| FR-116 | Optional: pickup only, delivery available, or both | ✅ |

> **Three of these waited on a `bookings` table, and were marked honestly rather than ticked until
> it existed. Two are now closed.**
>
> - **FR-112 cannot be built here at all.** "Changing the rate card never alters an already-confirmed
>   booking" is a guarantee a *booking* provides, by copying the agreed price into itself at the
>   moment it is confirmed. An owner editing a rate — which FR-108 explicitly permits — is precisely
>   the event FR-112 exists to survive, so refusing the edit would be the wrong fix. **Still ⬜ here
>   deliberately**: it is satisfied by `bookings`' frozen price columns, and it is ticked in the
>   bookings section rather than twice.
> - **FR-110 is enforced, and STRICTER than its own wording.** The requirement says a listing may be
>   deleted "only when no active or upcoming booking exists", implying one with nothing but old
>   completed bookings could go. It cannot: `bookings.listing_id` is `ON DELETE RESTRICT`, so *any*
>   booking blocks the delete. That is deliberate — a completed booking is the other party's record
>   of what they rented and paid, and deleting the listing would leave a receipt pointing at
>   nothing. The remedy offered in the error is to unpublish.
>   **The refusal arrives as SQLSTATE `23001`, not `23503`** — a RESTRICT violation is
>   `restrict_violation`, and assuming the ordinary foreign-key code is how this first surfaced as a
>   500.
> - **FR-109's second half is now tested**, not merely believed: a confirmed booking survives its
>   listing being unpublished, stays `ACCEPTED`, and stays readable **by the renter** — who is not
>   the owner and therefore cannot see an unpublished listing at all. That is the case worth
>   pinning, because it is the one where reading a booking could accidentally have been made to
>   depend on the listing still being visible.

## Availability — step 4 ✅

Spec: [`features/07-availability.md`](features/07-availability.md)

| ID | Requirement | Status |
|---|---|---|
| FR-200 | Owner declares blackout dates | ✅ |
| FR-201 | A confirmed booking blocks its dates automatically | ✅ |
| FR-202 | **Two confirmed bookings can never overlap for one listing** — enforced by a database exclusion constraint, not an application check | ✅ — migration 006 |
| FR-203 | Notice period: earliest a listing can be booked from | ✅ |
| FR-204 | Owner sees a calendar of bookings and blackouts | ✅ |
| FR-205 | Availability shown on the public listing page | ✅ |
| FR-206 | Blackout dates cannot be added over an existing confirmed booking | ✅ — trigger, not a service check |

> **Built out of order, and that was the right call.** Five of these seven need a `bookings` table
> to mean anything, so step 4 was done after step 6. FR-201 and FR-202 were in fact already
> satisfied by migration 006 before step 4 started — a confirmed booking has always blocked its own
> dates, because `findUnavailablePeriods` reads `bookings` and `availability_blocks` through one
> `UNION ALL` rather than tracking availability separately. **There is no derived availability
> table to keep in sync**, which is the bug this shape exists to make impossible.
>
> **FR-206 is a trigger and FR-202 is an EXCLUDE constraint, and the difference is not arbitrary.**
> FR-202's rule is between two rows of one table, so Postgres can settle it inside a single index
> and the guarantee is airtight. FR-206 spans two tables, which no EXCLUDE can express — so it is a
> trigger, and under READ COMMITTED it has a residual write-skew window. That is accepted, and
> `007_create_availability.sql` records why: a double booking promises one person's camera to two
> strangers, whereas an overlapping blackout is an owner contradicting their own calendar, visible
> to them and harming nobody else.
>
> **FR-204 and FR-205 are one endpoint and one component, differing by a single field.**
> `GET /listings/:id/availability` adds `kind` for the owner and omits it for everybody else, and
> `AvailabilityCalendar` decides what to render from whether that field arrived — so a visitor
> cannot be shown a distinction that never reached the browser. The owner's *editable* list is a
> separate owner-only endpoint, because an id is a handle for deleting a row and a reason is a
> private note; neither may travel on a world-readable path.

## Browse & search — step 5 ✅

Spec: [`features/05-browse.md`](features/05-browse.md)

| ID | Requirement | Status |
|---|---|---|
| FR-300 | Browse published listings **without an account** | ✅ |
| FR-301 | Filter by category | ✅ |
| FR-302 | Filter by price range, per chosen rental unit | ✅ |
| FR-303 | Filter by available dates | ✅ — step 4 |
| FR-304 | Filter by locality / city | ✅ — by city; locality is shown, not filtered on |
| FR-305 | Text search on title and description | ✅ — trigram, so partial words match |
| FR-306 | Sort by price, newest, rating | 🟡 — price and newest done; **rating needs reviews** (step 9) |
| FR-307 | Paginated, defaulted and capped; `total` counted with the **same WHERE** as the page | ✅ |
| FR-308 | Public listing detail page, no account needed | ✅ — built at step 3 |
| FR-309 | Unpublished, draft and deleted listings never appear | ✅ |
| — | **Your own listings never appear in your own browse results** | ✅ — the other half of FR-502, see below |
| FR-310 | A listing shows its owner's public profile and rating | 🟡 — links to the profile; **rating needs reviews** |

> **FR-307 is stronger than it asks for.** It requires `total` to be counted with the same WHERE as
> the page; the implementation takes it from the *same statement*, via `count(*) OVER ()`. Sharing a
> clause relies on discipline, sharing a statement makes disagreement impossible — and the failure
> it prevents is silent: a pager offering a page four that renders empty.
>
> **FR-304 filters by city, not locality.** Locality is displayed on every tile and detail page but
> is free text an owner types, so it has no canonical list to filter from — "Kothrud" and "Kothrud,
> Pune" would be different filters. City comes from the same free text and has the same weakness in
> principle, but a short derived list is usable in a dropdown where a long one is not. A real fix is
> a places lookup table, which is not worth it at this size.
>
> **A signed-in visitor does not see their own listings while browsing**, and this is not a filter
> anyone chose — it is FR-502 applied one step earlier. You cannot book your own item, so showing it
> among things you can rent is a dead end: click through and the only action on the page is one the
> server will refuse. Your own items live in Your listings, which is a different job — an inventory
> to manage rather than a shelf to shop from.
>
> - **A `WHERE` condition, not a separate section in the results and not a filter in JS.** `total`
>   comes from `count(*) OVER ()`, so excluding rows anywhere other than the query would leave the
>   pager promising a page it had withheld. There is a test for exactly that.
> - **`GET /listings` therefore takes `attachUserIfPresent`**, having previously had no auth
>   middleware at all on the grounds that "the result does not vary by who is asking". It does now.
>   Signed out, there is nobody to exclude and the whole catalogue is returned.
> - **The UI says so**, because a silent exclusion is indistinguishable from a bug — the first thing
>   an owner would otherwise notice is that the listing they just published is missing.
>
> **FR-303 landed with step 4.** It is a `NOT EXISTS` against bookings and blackouts, chosen over a
> join deliberately: a join would need a `DISTINCT` to avoid multiplying a listing by its bookings,
> and a `DISTINCT` breaks `count(*) OVER ()` — which is what FR-307 relies on to keep the total and
> the page structurally inseparable. It also excludes a listing whose notice period has not yet
> elapsed, so the filter answers "can I actually book this" rather than only "is it free".
>
> **Both dates or neither, and the server refuses a half-open range with a 400.** The client
> therefore sends nothing until both are filled, rather than turning a half-completed form into an
> error message.

## Pricing & quotes — step 6 ✅ (bookings still to come)

The product's least obvious behaviour: [`0.product-overview.md`](0.product-overview.md) §4

| ID | Requirement | Status |
|---|---|---|
| FR-400 | **Charge the cheapest applicable combination of rates**, never a naive multiplication | ✅ |
| FR-401 | Show an **itemised breakdown** before booking: units, rate applied, subtotal | ✅ — API returns it; the UI lands with bookings |
| FR-402 | Deposit shown separately from rent, and labelled refundable | ✅ |
| FR-403 | Platform commission computed and recorded, not implied | ✅ — computed; **recorded** when `bookings` exists |
| FR-404 | **Quotes are computed server-side only.** A client-supplied total is never trusted | ✅ |
| FR-405 | A quote is recomputed at booking time; a stale one is refused | ⬜ — needs booking |
| FR-406 | Tax (GST) as a field from the first migration, even at zero | ✅ |
| FR-407 | Partial periods round in the renter's favour where ambiguous, and say so | ✅ |

> **The algorithm is exhaustive, not greedy, and that is the correctness argument.** Greedy — take
> as many months as fit, then days, then hours — gets the 40-day example right and the **6-hour one
> wrong**: six hours do not fill a day, so filling downward never considers buying one, and charges
> ₹900 where ₹800 was available. Rounding *up* to a larger unit is frequently the cheapest answer.
> The search space is tiny (durations are capped at a year), so exhaustive search costs microseconds
> and removes the need to reason about which rate relationships hold.
>
> **FR-407 in practice:** the duration rounds up to whole hours once, never per line, so it cannot
> compound — and since the combination chosen is always the cheapest, the rounding never costs the
> renter more than the unit they are being sold. A tie prefers fewer invoice lines, then larger
> units, so "1 month" beats "30 days" at the same money. That tie rule was **wrong on the first
> pass** and a test caught it.
>
> **Commission is taken from the owner's payout, not added to the renter's bill**, so the quoted
> price is the price paid. Nothing collects it — there is no gateway until step 10 — but the figure
> exists now because a commission introduced later would have to be back-computed for every
> historical booking.

| FR-505 | States: `REQUESTED → ACCEPTED → ACTIVE → RETURNED → COMPLETED`, plus `DECLINED`, `CANCELLED`, `EXPIRED` | ✅ — all declared; the handover three are wired at step 8 |
| FR-506 | Illegal transitions refused server-side with `409`; the map lives in **one place** | ✅ |
| FR-507 | Owner accepts or declines, with an optional message | ✅ |
| FR-508 | A request not answered within N hours **expires automatically** | ✅ — 48h, swept hourly by `scheduler.js` |
| FR-509 | Renter may cancel before handover; policy determines the refund | 🟡 — cancel done; **refund policy needs payments** (step 10) |
| FR-510 | Owner may cancel, and it counts against their reliability | 🟡 — a distinct action, recorded; **no reliability score yet** |
| FR-511 | **Every state change recorded with actor, timestamp and comment — append-only** | ✅ — enforced by a trigger, not a convention |
| FR-512 | Both parties see the booking; **nobody else does** | ✅ |
| FR-513 | Renter sees their bookings; owner sees bookings on their listings | ✅ |
| FR-514 | **20 concurrent requests for the same dates produce exactly one confirmed booking** | ✅ |

> **FR-514 is not something the application achieves — it is something it cannot prevent.** An
> `EXCLUDE USING gist` constraint on `(listing_id WITH =, period WITH &&)` decides it inside
> Postgres, so twenty simultaneous accepts produce one winner whatever order they arrive in. An
> application check reads "is there an overlap?" and then inserts; the gap between those two is
> where the double booking lives, and no amount of care in the service closes it. **Verified with a
> test that fires twenty concurrent accepts and asserts 1 accepted / 19 refused.**
>
> The constraint is **partial** — `WHERE status IN ('ACCEPTED','ACTIVE')`. `REQUESTED` deliberately
> holds nothing: several people may ask for one weekend and the owner picks. Blocking at request
> time would make the fastest requester win rather than the owner choosing.
>
> The range uses `[)` bounds, so a booking ending at 10:00 and one starting at 10:00 do not
> overlap — with inclusive ends, every back-to-back handover in the product would be refused.
>
> **FR-510 is a separate action from FR-509, not the same one with a different actor.** Two actions
> mean the trail records which happened without inferring it from an actor id, and a reliability
> score becomes a row count rather than a join.
>
> **FR-511 is enforced by a trigger** that refuses UPDATE and DELETE on `booking_events`. A
> convention is worth nothing here: the one time somebody fixes a typo with an UPDATE, the trail
> stops being evidence.
