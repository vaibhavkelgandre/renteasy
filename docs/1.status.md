### The guarantees that are pinned by tests

Not "it works" but "it cannot silently stop working":

- three registration attempts — new, unverified, verified — return **`toEqual`-identical** bodies
- the password is hashed on **every** path, so timing cannot rebuild the enumeration oracle
- expired, used, unknown and malformed tokens answer **byte-identically**
- only the token **hash** reaches the database
- `is_admin` / `status` in a request body are silently stripped
- with the mail transport forced to throw, registration still answers `202` **and** the user row and
  token both exist
- verification reflects on `/auth/me` **immediately**, without signing out
- the "check your inbox" page contains none of *"account created"*, *"we've sent you a link"*,
  *"already registered"*, *"welcome"*
- `/verify/:token` is consumed **exactly once** AND still **reports its answer**, asserted with the
  tree rendered inside a real `<StrictMode>` — the earlier version of this test named StrictMode
  without entering it, and a permanent loading spinner shipped past it
- a reset request answers **`toEqual`-identically** for a live, suspended, unknown and
  cooldown-blocked address, and mail goes to the live one only
- unknown, expired, used and malformed **reset** tokens answer byte-identically
- four simultaneous submissions of one reset token produce exactly **one** `200` and three `410`s
- a reset token dies if the account's email changes, or if the account is suspended
- a reset issues **no cookie**, and never answers `409` under concurrency
- `/reset-password/:token` makes **no request on page load** — a prefetching mail client must not
  spend the token

## 5. Pending — the near list

Ordered by how much they actually block something.

### 5.1 Real email — ✅ **live, confirmed against a real inbox**

`config/mailer.js` has four modes. The first two are chosen by environment, the last two by whether
a provider is actually configured:

| Mode | Behaviour |
|---|---|
| test | in-memory outbox, **first and unconditional** — the suite cannot reach the network |
| development | console, **including the link**, whether or not a provider is configured |
| configured | **Brevo**, one JSON POST over HTTPS, no SDK |
| production, unconfigured | refuses, loudly — logs the address and subject, **never the body** |

**Confirmed working on 9 September 2026**: a real registration delivered a real verification email
via Brevo, and the link verified the account.

**The send decision is configuration-driven, not another `NODE_ENV` branch.** The reason to want
real mail locally is to test against a real inbox, and keying that on the environment would mean
editing code to do it. Paste a key into `server/.env` and mail goes out — locally too.

**Not yet exercised against a real inbox: the password reset email.** Same transport, so the risk is
low, but it has never actually been delivered.

**To switch it on**, two lines in `server/.env` (both, or it reads as unconfigured):

```
BREVO_API_KEY=xkeysib-...
MAIL_FROM=RentEasy <your-verified@address>
```

Three things about the account, each of which has already cost somebody an afternoon on the other
project:

- **The key must come from Brevo's *API Keys* tab and start `xkeysib-`.** The adjacent *SMTP* tab
  issues an `xsmtpsib-` credential which this HTTP endpoint rejects with `Key not found` — a message
  that reads as a wrong key rather than the wrong *kind*. First thing to check on a 401.
- **A second key, not the one the other project uses.** Quota is shared per *account* either way;
  separate keys mean either app can be revoked without taking the other down. RentEasy is the one
  with public signup, so it is the riskier of the two.
- **Account-level click tracking must stay off.** Every link this app mails is a single-use
  credential, and Brevo has no per-send tracking switch — so this cannot be enforced from the code,
  only recorded here.

**Quota is 300/day, shared with the other project.** Registration is rate limited to 10/hour per IP,
which bounds abuse but does not stop RentEasy eating the shared allowance — the argument for a
separate Brevo account if this ever takes real traffic.

**Known gap: the Brevo branch itself has no automated test.** The in-memory outbox guard runs ahead
of every other branch precisely so the suite can never send, which also puts the send path out of
the suite's reach. What is covered: that the guard holds even when fully configured, the `MAIL_FROM`
parsing including both quoting mistakes, and that a key alone never reads as configured. The request
shape, both failure paths and the production refusal were verified by a stubbed-`fetch` probe rather
than a committed test.

### 5.2 Media storage — decided, not built

[6.media-storage.md](6.media-storage.md) settles the provider, the public/private split, the upload
path and the orphan handling. Nothing is implemented — it lands with listings at step 3.

**The one thing in there that is a safety issue rather than a preference: EXIF must be stripped on
upload.** A phone photo carries GPS coordinates, so publishing a listing photo would otherwise
publish the owner's home address.

### 5.3 A password reset does not sign out other sessions

The largest remaining security gap, and it is now the one worth doing next of these. A JWT is signed
over the user id, not the password hash, so a session stolen **before** a reset stays valid for up to
12 hours after it — which undercuts the main reason people reset a password at all. The same is true
of changing a password from the account page.

Needs a `token_version` integer on `users`, carried in the JWT and compared in `requireAuth`. Roughly
one migration and forty lines. See [features/02](features/02-password-reset.md) §7.

## 6. Built but not wired to anything

Recorded honestly rather than counted as done. Each is correct code with **no consumer**, so nothing
proves it works in place:

| Thing | Note |
|---|---|
| `requireVerifiedEmail` | **0 routes use it.** The gate that makes FR-005 real — it starts mattering at step 3, when there is finally something to gate (creating a listing). Until then, "unverified users cannot list" is a design intention, not an enforced rule. **Deliberately not used on the profile routes**: someone whose address was mistyped at signup is exactly who needs to change it, and gating that would trap them permanently |
| `requireAdmin` | 0 routes. No admin endpoints exist yet |
| `validateQuery` | Written; no endpoint takes a query string yet. `validateParams` now has one (`GET /users/:id/public`) |

**Three left this table with the profile feature**, and each was worth the wait rather than a
formality:

| Was unwired | First consumer | Did it work? |
|---|---|---|
| `RequireAuth` (client) | `/profile`, the first authenticated page | Yes — a test asserts a signed-out visitor lands on sign-in |
| `validateParams` | `GET /users/:id/public` | Yes — a malformed id answers a 404 identical to an unknown one |
| `invalidateResetTokensForUser` | Confirming an email change, and changing a password | Yes — both pinned by tests |

**This pattern has bitten before.** In an earlier project a role gate sat unused for a whole step
and, when it finally got a consumer, needed a fix. Treat everything in this table as unverified until
something real depends on it.

## 7. Decisions taken, so they are not re-litigated

| Decision | Where |
|---|---|
| Email is the identity, not phone | Confirmed directly. Phone captured at signup, verified later as a trust tier |
| Registration answers `202`, identically, always | [features/01](features/01-public-registration.md) §3.1 |
| Registration does not sign you in | §3.2 |
| An unverified user **can** sign in | §3.3 |
| A token verifies an address, not a user | §3.4 |
| No role hierarchy — authorization is relationship-based | [0.product-overview.md](0.product-overview.md) §2 |
| Money is integer paise; totals derived, never stored | §2 |
| V1 is portable goods only; property deferred | §7 |
| Charge the **cheapest applicable** rate combination | §4 |
| Ports 5001 / 5174, not the framework defaults | [troubleshooting.md](troubleshooting.md) |
| Media on **Cloudinary**, chosen for delivery-time transformations rather than familiarity | [6.media-storage.md](6.media-storage.md) §3 |
| Listing photos are **public** objects; documents will be **private**. Different pipelines | §4 |
| Postgres stores a `storage_id`, **never a URL** | §6 |
| EXIF stripped on upload — a phone photo carries **GPS** | §5 |
| A reset link lasts **1 hour**, against verification's 24 | [features/02](features/02-password-reset.md) §4 |
| A reset **does not sign you in** | §3.3 |
| A reset does **not** mark the email verified, though it could | §3.6 |
| Reset and verification tokens are **separate tables**, not one with a `purpose` column | §2 |
| Claiming a reset token and setting the password is **one SQL statement** | §3.7 |
| The reset page **does not spend its token on load** — mail clients prefetch | §3.4 |
| An email change is **pending** until proved; the old address keeps working | [features/03](features/03-profile.md) §3.2 |
| Changing an email discloses nothing about who owns the target address | §3.1 |
| Email, phone, status and `is_admin` are **unreachable** from the profile update endpoint | §3.3 |
| Deletion is **soft**, and the address is **not** released | §3.5 |
| A public profile is a four-column projection, never a filtered row | §3.6 |
| `/terms` says it is placeholder text rather than inventing legalese | §3.7 |

## 8. Known limitations

Named deliberately, so they are gaps rather than oversights.

- **No payment gateway.** The money *model* comes at step 10; the gateway later. An invoice will
  never be marked paid because the frontend said so — only on server-side verification of a webhook.
- **No property rentals.** Needs agreements, longer terms and local legal compliance.
- **No social sign-in, no CAPTCHA, no disposable-domain blocking.**
- **No account deletion**, which data-protection law will eventually require.
- **A password reset does not sign out other sessions, and this is now the most significant gap.**
  A JWT is signed over the user id, not the password hash, so a session stolen *before* a reset stays
  valid for up to 12 hours after it — which undercuts the main reason people reset a password at all.
  Fixing it needs a `token_version` column on `users`, carried in the JWT and compared in
  `requireAuth`. See [features/02](features/02-password-reset.md) §7.
- **No "your password was changed" email.** Standard practice, and the thing that tells a real owner
  their account was taken. Deliberately out of scope for FR-020–027; wants its own requirement.
- **Rate-limit counts are per process and reset on deploy** — in-memory store. Correct for one
  instance; a second would need a shared store before the numbers mean anything.
