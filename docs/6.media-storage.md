# 6. Media storage

How listing photos — and later, verification documents — are stored, served and cleaned up.

**Status: BUILT** (step 3, migration 004). Everything below describes what now exists —
`server/src/config/cloudinary.js` is the only module that knows where images live, and it exports
functions rather than a client precisely so the R2 move in §3 stays a one-file change.

Two things differ from what was planned here, both noted in place: the `cloudinary` SDK *is* used
(§5), and `listing_photos` carries a **DEFERRABLE** unique constraint (§6).

---

## 1. The requirement, stated properly

A marketplace lives or dies on its photos. Someone deciding whether to rent your camera looks at
pictures first and reads second. So this is not "file upload" — it is:

- **6–8 photos per listing**, taken on a phone, typically 3–5 MB each
- a **grid** of listings on mobile data, where a 4 MB image per tile is fatal
- a **detail page** that wants something sharper
- images that must stay available for years and survive a server rebuild

## 2. What is ruled out, and why

| Option | Verdict |
|---|---|
| **Bytes in Postgres** (`bytea`) | ❌ Bloats the database, makes every backup enormous and slow, and puts image traffic through the connection pool. Postgres is not a file server |
| **Local disk on the app server** | ❌ A container restart or a redeploy wipes it, a second instance cannot see it, and there is no CDN. The one arrangement where it survives — a VM with a mounted volume — still needs its own backup story |
| **Object storage + CDN** | ✅ The only answer that survives a rebuild and serves a grid quickly |

**The general principle, worth keeping past this decision: a server you can recreate from scratch is
a server you can afford to lose.** Anything irreplaceable on the app server's disk breaks that.

## 3. Decision: Cloudinary

**Because of transformations, not familiarity.**

A listing grid needs a ~400px thumbnail, a detail page needs ~1200px, and a zoom wants the original.
Something has to produce those three. The two ways:

| | Generate variants yourself | Transformation on delivery |
|---|---|---|
| Code | `sharp` in the upload path | a URL parameter |
| Native dependency | **yes** — `sharp` is a real deploy and Docker headache | none |
| CPU | yours, on upload | theirs |
| Storage | **3× the files** | 1× |
| Changing a size later | **re-process every existing image** | edit a string |

That last row is what settles it. On a portfolio project the sizes *will* change once, and
re-processing everything is the kind of chore that never happens — so the grid stays slow.

**Alternative considered: Cloudflare R2.** 10 GB free with **zero egress fees**, which is genuinely
better than anything else for pure storage. Rejected here only because it has no built-in
transformation — Cloudflare Images is a paid add-on, so R2 puts us back in the left column above.
**If bandwidth ever becomes the binding cost, R2 plus generated variants is the right move**, and
§6's "store an id, never a URL" rule is what keeps that migration cheap.

Free tier: 25 GB storage and 25 GB monthly bandwidth, no card, no expiry.

## 4. The important difference from a document store

> **Listing photos are PUBLIC objects. Verification documents are PRIVATE ones. They must not share
> a pipeline.**

This is worth stating loudly because it is easy to reach for a private-by-default setup out of
caution and make the product worse:

| | Listing photos | ID / verification documents (later) |
|---|---|---|
| Audience | **everyone browsing, signed in or not** | the owner, and an admin reviewing |
| Delivery | plain CDN URL | short-lived **signed** URL, minted per request |
| Cacheable | **yes — by the CDN, the browser, everything** | no |
| Upload type | `public` | `authenticated` |

**Signing a public image is not extra safety, it is a bug.** A signed URL expires, so the CDN cannot
cache it, every visitor re-fetches from origin, and a grid of 20 listings needs 20 freshly minted
URLs per page load. The content is public *by design* — the whole point of a listing is that
strangers see it.

Documents get the opposite treatment for the opposite reason, and that pipeline is built later, with
its own folder and its own upload type.

## 5. Upload path: through the server, for V1

```
browser ──multipart──▶ our API ──▶ Cloudinary ──▶ public_id
                          │
                          └──▶ Postgres row
```

**Not direct-from-browser yet.** A signed direct upload (browser → Cloudinary, using a short-lived
signature our server issues) is faster and never puts the bytes through our server. It is the right
end state and it is named here as the upgrade — but it is more moving parts, and going through the
server keeps validation in exactly one place while there is one upload surface to get right.

> **Built as specified, with one deviation: the `cloudinary` SDK is a dependency.** `config/mailer.js`
> deliberately has no provider SDK because Brevo's send is one JSON POST. A Cloudinary upload is a
> multipart POST whose signature is a SHA-1 over sorted parameters — a real algorithm with a real
> chance of being subtly wrong, and a wrong signature fails identically to a wrong key. The SDK is
> the reference implementation of exactly that; the functions-only wrapper is what stops it
> spreading past one file.

**The validation that has to be there from day one:**

| Rule | Why |
|---|---|
| **Real type sniffed from the first bytes** — never the extension, never the client's `Content-Type` | Both are attacker-supplied. `evil.jpg` can be anything |
| **JPEG / PNG / WebP only** | No SVG: it is a document, can carry script, and would be served from our CDN domain |
| **5 MB per file, 8 files per listing** | A phone photo is 3–5 MB; the cap bounds a request rather than restricting anyone |
| **Multer memory storage** | The bytes never touch our disk, so there is nothing to clean up if a request dies |
| **Strip EXIF** | A phone photo carries **GPS coordinates**. Publishing a listing photo would otherwise publish the owner's home address. Done with an **incoming transformation**, which replaces the stored original — NOT with `image_metadata`, which only controls what the API returns. See [features/04](features/04-listings.md) §3.5 |

**That last one is the non-obvious one and it matters most.** A marketplace where every listing photo
leaks the owner's exact location is a safety problem, not a privacy footnote.

**Order of operations, and it is deliberate:**

1. validate the request body
2. check the caller owns the listing
3. validate every file (type, size, count)
4. **upload to Cloudinary**
5. **insert the Postgres rows**

Uploading *after* every other check and *before* the insert means a rejected request never creates a
remote asset, and a failed upload never leaves a half-created listing — nothing has touched Postgres
at that point.

## 6. What Postgres stores

```sql
CREATE TABLE listing_photos (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  listing_id   uuid NOT NULL REFERENCES listings(id) ON DELETE CASCADE,

  -- The provider's own identifier. NEVER a URL.
  storage_id   text NOT NULL,
  provider     text NOT NULL DEFAULT 'CLOUDINARY',

  -- Returned by the upload. Lets the frontend reserve the right space before the
  -- image arrives, which is what stops a grid jumping as photos load.
  width        integer NOT NULL,
  height       integer NOT NULL,
  bytes        integer NOT NULL,
  mime_type    text NOT NULL,

  -- Position 0 is the cover, the one that appears in the grid. Ordering rather than a
  -- separate `is_cover` flag: with a flag, "exactly one cover" is an invariant to
  -- enforce, and a listing whose cover was deleted has none.
  sort_order   integer NOT NULL DEFAULT 0,

  created_at   timestamptz NOT NULL DEFAULT now(),
  -- DEFERRABLE INITIALLY DEFERRED as built, which the original sketch did not say.
  -- Reordering permutes these values and a permutation passes through states where two
  -- rows share a position, so a normal UNIQUE refuses every reorder that is not a
  -- strict rotation. Deferred, the check happens at commit and one statement can
  -- rewrite the whole order.
  CONSTRAINT uq_listing_photo_position UNIQUE (listing_id, sort_order)
    DEFERRABLE INITIALLY DEFERRED
);
```

**`storage_id`, never a URL — the single most important rule on this page.**

A URL bakes in the provider, the account, the CDN domain, the delivery scheme *and* the transformation
into a value stored on thousands of rows. Change any one of them — move to R2, put a custom domain in
front, resize the thumbnail — and it is a data migration across the whole table. Storing an id makes
every one of those a change to one function:

```js
thumbnailUrl(storage_id)  →  .../w_400,h_300,c_fill,f_auto,q_auto/<storage_id>
detailUrl(storage_id)     →  .../w_1200,c_limit,f_auto,q_auto/<storage_id>
```

**`f_auto,q_auto` are not decoration:** `f_auto` serves WebP or AVIF to browsers that accept them and
JPEG to those that do not, and `q_auto` picks a quality per image. Together they routinely halve the
bytes for no visible difference — which on a marketplace grid over mobile data is the difference
between usable and not.

## 7. Orphans and deletion

Two failure directions, and they need different answers.

**An asset with no row.** An upload succeeds and the insert then fails. The order in §5 makes this
rare, but a crash between the two is possible. Accepted for V1 — it costs storage and nothing else —
with a **sweep** listing Cloudinary assets in the listings folder that have no matching row. Written
as a script, run manually, never on a schedule until it has been watched once.

**A row with no asset.** Deleting a listing cascades its rows; the remote delete is a separate call
that can fail. So the remote delete is **fire-and-forget after the transaction commits**, logged on
failure. Deleting the row is the operation that matters — a leftover asset is a storage cost, whereas
a failed delete that rolls back the whole transaction would leave the user unable to delete their
listing at all.

## 8. Known gaps, named deliberately

- **No moderation.** A public marketplace where anyone uploads images *will* receive content that
  should not be there. V1 has no review step and no report button. Real, and out of scope — but it
  should be a deliberate decision rather than a discovery.
- **No virus scanning.** Mitigated by accepting only three raster formats and sniffing the real type,
  which is most of the practical risk for images.
- **No duplicate detection.** The same photo uploaded twice is stored twice.
- **Direct-from-browser upload** — the named upgrade in §5.
- **No image dimensions minimum.** A 100×80 photo will look terrible in a grid; nothing currently
  refuses it.
