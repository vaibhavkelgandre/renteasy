# 3. Database schema

**Standing rule: any migration added under `server/src/sql/` updates this file in the same commit.**

PostgreSQL. UUID primary keys, raw parameterised SQL, no ORM.
Databases: `renteasy` (dev) and `renteasy_test`.

Applied migrations: **9** (`001` … `009`).

---

## `users`  ✅ migration 001

Identity only. **Note what is absent: there is no `role` column.** The same person lists a camera and
rents a bike, so "owner" and "renter" are relationships to a listing or a booking, never properties
of a person. `is_admin` is platform staff, who are not marketplace participants at all.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()` |
| `name` | `text` NOT NULL | Shown to whoever hands over the item |
| `email` | `text` NOT NULL | **`UNIQUE` on `lower(email)`** |
| `password_hash` | `text` NOT NULL | bcrypt. Never logged, never returned |
| `email_verified_at` | `timestamptz` NULL | **NULL = unverified** |
| `phone` | `text` NULL | Verified later as a trust tier. **Not unique** — households share numbers |
| `phone_verified_at` | `timestamptz` NULL | Unused so far |
| `status` | `text` NOT NULL | `ACTIVE` \| `SUSPENDED` \| `DELETED` |
| `is_admin` | `boolean` NOT NULL | Default false. **Never settable from a request body** |
| `accepted_terms_version` | `text` NOT NULL | Which terms, not merely that they agreed |
| `accepted_terms_at` | `timestamptz` NOT NULL | |
| `created_at` / `updated_at` | `timestamptz` | |

**`UNIQUE (lower(email))`, on the expression.** A plain constraint on `email` treats `Priya@x.com`
and `priya@x.com` as two accounts — and then whoever registered first cannot sign in with the casing
they remember, while the error reads "invalid credentials" and sends everyone hunting the wrong
problem.

**`email_verified_at` is a nullable timestamp, not a boolean.** It answers both "is it verified" and
"since when", and it makes the invalid state — verified, but nobody knows when — unrepresentable.

**`accepted_terms_version` is why terms acceptance is worth anything.** "They ticked a box" tells you
nothing later; "they accepted version 2026-09-01 at this time" does.

Indexes: `uq_users_email_lower` · `idx_users_status`.

> ### Added by migration 003 — the profile feature
>
> | Column | Type | Notes |
> |---|---|---|
> | `pending_email` | `text` | **The address a user wants to move to, not the one they have.** FR-030 requires the old address to keep working until the new one is proved, so a change cannot overwrite `email` — overwriting would mean a typo locks the account out permanently, since the new address never receives the link and the old one is already gone. **Deliberately NOT unique and not indexed:** two people may both have a pending change to the same address, which is not a conflict because nothing has happened yet. The winner is decided at confirmation by `uq_users_email_lower`. A unique constraint here would let the first person to *request* an address reserve it forever without ever proving they own it — a denial of service on somebody else's real email |
> | `deleted_at` | `timestamptz` | Paired with the pre-existing `status = 'DELETED'`. A nullable timestamp rather than status alone, so it answers "since when" too — same reasoning as `email_verified_at`. Deletion is **soft**: a marketplace's bookings and reviews reference a person, and the counterparty to a completed rental is entitled to their own history, so a hard `DELETE` would either cascade those away or be refused by a foreign key |
>
> **The consequence of soft deletion, named because it is user-visible:** the row survives, so
> `uq_users_email_lower` still holds that address and the person cannot re-register with it.
> Releasing it needs a scrub step (overwrite `email` with a tombstone) that is not built.
>
> **`pending_email` is promoted by `confirmEmailChange`, which sets `email`, clears
> `pending_email` and stamps `email_verified_at` in ONE statement** — any two of those apart is a
> broken state. An address moved but not marked verified locks a real owner out of verified-only
> features; a `pending_email` left behind would let the same token be replayed.

## `email_verification_tokens`  ✅ migration 001

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `user_id` | `uuid` NOT NULL | → `users(id)` ON DELETE CASCADE |
| `token_hash` | `text` NOT NULL **UNIQUE** | **SHA-256 only.** The raw token is never stored |
| `email` | `text` NOT NULL | The address this token was issued **for** |
| `expires_at` | `timestamptz` NOT NULL | 24 hours |
| `used_at` | `timestamptz` NULL | Single use |
| `created_at` | `timestamptz` NOT NULL | Drives the resend cooldown |

**Only the hash.** A database leak must not hand over the ability to verify — and therefore
activate — every pending account. Plain SHA-256, not bcrypt: a 256-bit random token has no
low-entropy secret to defend, and a slow hash would only cost every click 60ms.

**`email` is the guard that makes a token prove something specific.** Consuming it verifies the user
only if `users.email` still matches. Without it, *register as `a@x.com` → change email to `b@y.com`
→ click the old link* would mark `b@y.com` verified having proved nothing about it.

**The partial unique index is what makes reissuing atomic:**

```sql
CREATE UNIQUE INDEX uq_evt_active_user
  ON email_verification_tokens (user_id)
  WHERE used_at IS NULL;
```

At most one live token per user, so `INSERT ... ON CONFLICT (user_id) WHERE used_at IS NULL DO
UPDATE` replaces it in one statement. A select-then-delete-then-insert would let two concurrent
resends both mint a working link — and a user who clicks "resend" expects the old one to stop
working, which this guarantees.

Indexes: `UNIQUE (token_hash)` · `idx_evt_user (user_id, created_at DESC)` · `uq_evt_active_user`.

## `password_reset_tokens`  ✅ migration 002

Recovering a lost password. Spec: [features/02-password-reset.md](features/02-password-reset.md) §5.

**A separate table from `email_verification_tokens`, not one table with a `purpose` column.** The two
differ in every parameter that matters — 1 hour against 24, what consuming one does, and what a
leaked row grants (an account, versus a confirmed address). A shared table would mean every query
carrying a `WHERE purpose = …` that is a silent account-takeover bug the one time it is forgotten.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()` |
| `user_id` | `uuid` NOT NULL | → `users(id)` `ON DELETE CASCADE` |
| `token_hash` | `text` NOT NULL UNIQUE | **SHA-256 of the raw token, never the token.** The stakes are higher than for verification: a leak of raw reset tokens is a leak of live account-takeover credentials for every pending request |
| `email` | `text` NOT NULL | **The address it was emailed TO.** Consuming the token sets the password only if `users.email` still matches — otherwise "request a reset → change the account's email → click the old link" lets whoever holds the OLD address take the account. Also gives FR-031 for free |
| `expires_at` | `timestamptz` NOT NULL | **1 hour**, set by the repository rather than defaulted here, so the TTL is visible in the code that issues the token |
| `used_at` | `timestamptz` | NULL means live. Set by the atomic claim |
| `created_at` | `timestamptz` NOT NULL | `now()`. Drives the **15-minute** resend cooldown |

**`uq_prt_active_user`** — a partial unique index on `(user_id) WHERE used_at IS NULL`, so at most
one live token per user. It is what makes both reissuing and the cooldown a single atomic statement
(`INSERT … ON CONFLICT … DO UPDATE … WHERE created_at < now() - interval`), which in turn makes
three bugs unreachable: two concurrent requests both minting a link; the cooldown compared against a
JS clock rather than the database's; and a `23505` → `409` that would answer differently for
registered addresses only — an enumeration oracle.

Indexes: `UNIQUE (token_hash)` · `idx_prt_user (user_id, created_at DESC)` · `uq_prt_active_user`.

> **One statement writes this table and `users` together.** `consumeTokenAndSetPassword` claims the
> token and sets the password in a single data-modifying CTE — the only place `users` is written
> outside `userRepository.js`. With no transaction helper here, the two-statement version is wrong in
> both orders: consume-then-update burns the token and leaves the old password, while
> update-then-consume changes the password and leaves the link **live and replayable**.

## `categories`  ✅ migration 004

FR-102. Seeded with ten rows by the migration itself.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `slug` | `text` NOT NULL UNIQUE | The stable identifier — used in URLs, sent by the client, and readable in an error message. `name` is display text and may be reworded at any time |
| `name` | `text` NOT NULL | |
| `sort_order` | `integer` NOT NULL | Editorial, not alphabetical: the categories people actually browse come first |
| `is_active` | `boolean` NOT NULL | Retires a category **without** breaking listings that reference it |

**A LOOKUP TABLE, NOT A CHECK, and the reason is mechanical rather than stylistic.** There is no
`ADD VALUE` for a CHECK constraint — every change re-declares the whole list, so adding "drone" means
retyping twenty categories and the one you forget disappears silently. (This project has already been
bitten by exactly that shape elsewhere.) A category list grows with use, which is the test.

## `listings`  ✅ migration 004

Spec: [features/04-listings.md](features/04-listings.md).

| Column | Type | Notes |
|---|---|---|
| `owner_id` | `uuid` NOT NULL → `users` | `ON DELETE CASCADE`, though it will rarely fire — account deletion is soft, so the row and its listings survive |
| `category_id` | `uuid` NOT NULL → `categories` | **`ON DELETE RESTRICT`**, not CASCADE: deleting a category must never silently delete somebody's listings |
| `title`, `description` | `text` NOT NULL | |
| `condition` | `text` NOT NULL CHECK | `NEW / LIKE_NEW / GOOD / FAIR`. A **CHECK** here rather than a lookup table, and the contrast with `categories` is the point: this list is *closed*, tied to wording in the UI, and does not grow with use |
| `status` | `text` NOT NULL CHECK | `DRAFT / PUBLISHED / UNPUBLISHED`. **Three states, not a boolean** — a boolean cannot tell "never been visible" from "was visible, taken down", and they differ: one has a history and possibly live bookings |
| `hourly_rate_paise` `daily_rate_paise` `monthly_rate_paise` | `integer` NULL, `> 0` | **Integer paise, always.** All three nullable and no CHECK requiring one — see below |
| `deposit_paise` | `integer` NOT NULL `>= 0` | Zero is legitimate here, unlike a rate: "no deposit" is a real offer |
| `locality`, `city` | `text` NULL | **An AREA, never a street address** — FR-113 |
| `min_duration_hours` `max_duration_hours` | `integer` NULL | Hours throughout, so an hourly and a monthly listing are comparable without a second "unit" column to keep in sync. A table CHECK enforces `max >= min` |
| `fulfilment` | `text` NOT NULL CHECK | `PICKUP / DELIVERY / BOTH` |
| `published_at` | `timestamptz` NULL | When it FIRST went live. **Not cleared on unpublish** — "has this ever been visible?" is a different question from "is it visible now?", which `status` already answers |

> **Why no CHECK requiring at least one rate, when FR-103 says one is required.** A listing is
> created as a DRAFT (FR-100), and a draft is half-finished by definition — refusing to save one
> without a price would stop somebody who wants to think about the price overnight from starting at
> all. "At least one rate" is a **publish** condition (FR-107), enforced in the service alongside the
> rest of the gate. The same reasoning makes `locality` and `city` nullable.
>
> **`> 0` rather than `>= 0` on a rate**, because a rate of zero is not a free rental, it is a
> missing price. Free is expressible by leaving that unit unset.
>
> **There is deliberately no `address_line` column**, and adding one would be a safety regression
> rather than a feature: a published listing is world-readable, so a street address on it publishes
> where a valuable object is kept and where its owner lives.

Indexes: `idx_listings_owner (owner_id, created_at DESC)` for FR-115 · two **partial** indexes
`WHERE status = 'PUBLISHED'` for browse, so drafts are not carried in them at all.

## `listing_photos`  ✅ migration 004

Full reasoning: [6.media-storage.md](6.media-storage.md) §6.

| Column | Type | Notes |
|---|---|---|
| `listing_id` | `uuid` NOT NULL → `listings` | `ON DELETE CASCADE` |
| `storage_id` | `text` NOT NULL | **The provider's own identifier. NEVER a URL** — see below |
| `provider` | `text` NOT NULL | `CLOUDINARY` today |
| `width`, `height`, `bytes` | `integer` NOT NULL | Returned to the client so it can reserve the space before the image arrives, which stops a grid jumping as photos load |
| `mime_type` | `text` NOT NULL | The **sniffed** type, never the client's claim |
| `sort_order` | `integer` NOT NULL | Position 0 is the cover. Ordering rather than an `is_cover` flag: with a flag, "exactly one cover" is an invariant to enforce, and a listing whose cover was deleted has none |

> **`uq_listing_photo_position (listing_id, sort_order)` is `DEFERRABLE INITIALLY DEFERRED`, and
> that word is load-bearing.** Reordering permutes these values, and a permutation passes through
> states where two rows share a position — swapping 0 and 1 must transiently have two of one. A
> normal UNIQUE is checked per row as the statement runs, so it would refuse every reorder that is
> not a strict rotation. Deferred, the check happens at commit, so a single UPDATE can rewrite the
> whole order and only the final state is validated. Without it, reordering needs a temporary
> out-of-range value and three statements.
>
> **`storage_id`, never a URL — the single most important rule on this table.** A URL bakes the
> provider, the account, the CDN domain, the delivery scheme *and* the transformation into a value
> stored on thousands of rows. Change any one of them and it is a data migration; store an id and
> each is a change to one function.

## `bookings`  ✅ migration 006

Spec: [features/06-bookings.md](features/06-bookings.md).

| Column | Type | Notes |
|---|---|---|
| `listing_id` | `uuid` NOT NULL → `listings` | **`ON DELETE RESTRICT`**, unlike a photo's CASCADE: a booking is the *other party's* record and must outlive the listing. Raises **`23001`**, not `23503` — a RESTRICT violation is `restrict_violation`, and assuming the foreign-key code is how a delete came back as a 500 |
| `renter_id` | `uuid` NOT NULL → `users` | `ON DELETE RESTRICT`, same reasoning |
| `starts_at`, `ends_at` | `timestamptz` NOT NULL | CHECK `ends_at > starts_at` |
| `period` | `tstzrange` **STORED GENERATED** | `tstzrange(starts_at, ends_at, '[)')`. Derived, so it cannot disagree with the two columns it comes from |
| `status` | `text` NOT NULL CHECK | `REQUESTED / ACCEPTED / HANDED_OVER / ACTIVE / RETURNED / COMPLETED / DECLINED / CANCELLED / EXPIRED` — `HANDED_OVER` added by migration 008 |
| `rent_paise` `tax_paise` `deposit_paise` `commission_paise` `renter_total_paise` `owner_payout_paise` | `integer` NOT NULL `>= 0` | **The price is FROZEN at request time.** The rate card can change tomorrow; a booking cannot |
| `quote_lines` | `jsonb` NOT NULL | The itemisation as quoted, so an old booking can still be explained after the rates move |
| `renter_message` | `text` NULL | |

> **`bookings_no_double_booking` is the constraint this whole table is shaped around (FR-202).**
>
> ```sql
> EXCLUDE USING gist (listing_id WITH =, period WITH &&)
>   WHERE (status IN ('ACCEPTED', 'HANDED_OVER', 'ACTIVE'))   -- widened by 008
> ```
>
> **Partial**, because only a *confirmed* booking blocks the dates — several people may request
> the same weekend, and the owner picks one. **`[)` bounds**, so a rental ending at 10:00 and one
> starting at 10:00 are back-to-back rather than overlapping. Needs `btree_gist` for the `=` on a
> plain uuid alongside the range operator.
>
> Enforced by the database rather than by a service check, which is what makes it hold under
> concurrency — a check-then-insert has a window between the two, and a 20-way concurrent probe is
> what proves it does not.

Indexes: `idx_bookings_renter (renter_id, created_at DESC)` · `idx_bookings_listing (listing_id,
starts_at)` · a **partial** `idx_bookings_pending` for the owner's queue.

## `booking_photos`  ✅ migration 008

FR-702. Condition photos at handover and at return, by either party.

| Column | Type | Notes |
|---|---|---|
| `booking_id` | `uuid` NOT NULL → `bookings` | `ON DELETE CASCADE` — a photo of a handover means nothing without it |
| `phase` | `text` NOT NULL CHECK | `HANDOVER` / `RETURN`. **One table, not two** — the rows differ only in which moment they describe, and two tables would mean two upload paths and two chances for one to forget who may see it |
| `uploaded_by` | `uuid` NULL → `users` | **`ON DELETE SET NULL`** — deleting a user must erase the attribution, never the evidence. Stores WHO, not which role: a role is derived from the booking and would be a second copy of a fact it already owns |
| `storage_id` | `text` NOT NULL | The provider's id, **never a URL** — and more so here than for a listing, since these URLs are signed and expire, so a stored one would be a stored dead link |
| `note` | `text` NULL | The uploader's own words — "scratch on the lens barrel". The reason a photograph alone does not always settle anything |

> **PRIVATE storage, not the listing pipeline.** A listing photo is `type: "upload"` and
> world-readable, which is right for a shop window. These are taken wherever an item changes hands,
> so they show doorways, number plates, the inside of a home. They upload as `type: "authenticated"`
> — verified against the real provider, where the public URL form of such an asset answers **404**
> while a signed one answers 200 — and are served by a proxy that streams the bytes through this
> API after checking the caller is one of the two parties. **The signed URL never reaches the
> browser**, because it is a bearer credential for the five minutes it lives.
>
> **Append-only by trigger**, for the same reason `booking_events` is. This is evidence in a
> disagreement between two people about the condition of something, and the tempting exception —
> "let them delete one added by mistake" — is exactly the hole: *by mistake* is indistinguishable
> from *because it showed the scratch*. The cost is accepted: the remedy for a bad photo is another
> photo with a note.

Index: `idx_booking_photos_booking (booking_id, phase, created_at)`.

### Added by migration 008 — `idx_bookings_awaiting_confirmation`

Partial, on `(status, updated_at) WHERE status IN ('HANDED_OVER','RETURNED')` — FR-708's two
sweeps. **`updated_at`, not `created_at`**: what matters is how long a booking has sat in *this*
state, not how old it is, or a month-long rental would be swept the instant it was handed over.

## `availability_blocks`  ✅ migration 007

FR-200. Spec: [features/07-availability.md](features/07-availability.md).

| Column | Type | Notes |
|---|---|---|
| `listing_id` | `uuid` NOT NULL → `listings` | **`ON DELETE CASCADE`**, unlike `bookings.listing_id`'s RESTRICT. The difference is who else has a stake: a blackout is the owner's private note about their own item and means nothing once the item is gone |
| `starts_at`, `ends_at` | `timestamptz` NOT NULL | CHECK `ends_at > starts_at` |
| `period` | `tstzrange` **STORED GENERATED** | The same shape and the same `[)` bounds as `bookings.period`, deliberately — the two are compared constantly, and two notions of "overlap" in one product is a bug waiting for a boundary case |
| `reason` | `text` NULL | The owner's own note. **Never returned to a renter** |

> **A separate table rather than fake bookings**, which is the obvious shortcut and is wrong: a
> booking has a renter, a price and a state machine, none of which a blackout has. Modelling one as
> the other means a nullable `renter_id`, a status nothing can transition out of, and every booking
> query having to remember to exclude them.
>
> **`availability_blocks_no_overlap`** — `EXCLUDE USING gist (listing_id WITH =, period WITH &&)`,
> unpartitioned by status because a blackout has none. Tidiness rather than correctness: overlapping
> blackouts are harmless but make the owner's calendar unreadable, and merging them on read would be
> more code than forbidding them.
>
> ### `availability_blocks_vs_bookings` — FR-206, and the timing bug it shipped with
>
> A trigger, because the rule spans **two** tables and no EXCLUDE can express that. It is
> deliberately **AFTER INSERT OR UPDATE**, and that is not a style choice:
>
> `period` is a **stored generated column**, and Postgres computes those *after* row-level BEFORE
> triggers run. In a BEFORE trigger `NEW.period` is therefore `NULL`, `b.period && NULL` evaluates
> to `NULL` — which is not true — so the guard matched nothing and **every blackout was allowed**.
> It failed open, the worst way for a guard to fail: the first version looked correct and only a
> test that actually attempted the overlap found it. An AFTER trigger sees the computed value; the
> row is inserted and the exception rolls it back, which for a validation trigger is equivalent.
>
> **Weaker than FR-202's EXCLUDE, knowingly.** Under READ COMMITTED this is write skew: one
> transaction inserts a blackout while another accepts a booking for the same dates and neither
> sees the other. Closing it needs SERIALIZABLE or a lock on the listing, and the stakes do not
> justify either — a double booking promises one stranger's camera to two people, while an
> overlapping blackout is an owner contradicting their own calendar, visible to them and harming
> nobody else.

Index: `idx_availability_listing (listing_id, starts_at)`.

### Added by migration 007 — `listings.notice_period_hours`

FR-203. `integer` NULL, CHECK `>= 0`. On the **listing** rather than in its own table: it is a
property of the item ("I need a day's notice to fetch it from storage"), the same kind of fact as
the minimum rental duration that already lives there. Nullable means no notice required — the same
convention as the rates, so a draft is never refused for a field its owner has not reached.

## `notifications`  ✅ migration 009

FR-985, FR-986. Spec: [features/09-notifications.md](features/09-notifications.md).

| Column | Type | Notes |
|---|---|---|
| `user_id` | `uuid` NOT NULL → `users` | `ON DELETE CASCADE`. **The RECIPIENT** — a notification exists to be read by one person and has no meaning without them, unlike a booking, which is the other party's record too |
| `type` | `text` NOT NULL CHECK | **What happened, not who is told.** Encoding the audience here as well would double the list and turn "did the right person get this?" into a question about naming |
| `entity_type` / `entity_id` | `text` CHECK / `uuid` | What to open. **Not a stored path** — a URL is a client concern, and baking one in makes changing a route a data migration |
| `message` | `text` NOT NULL | The sentence, **stored** |
| `read_at` | `timestamptz` NULL | NULL means unread. A nullable timestamp rather than a boolean *plus* a timestamp: two columns that must agree is one more thing that can disagree, and a boolean cannot answer "when" |

> **One row per recipient, never a broadcast row.** "Read" is per-person: a shared row cannot be
> read by one party and unread by the other, and adding a `notification_reads` table to fix that is
> strictly more machinery than writing two rows. It is also the honest model for a two-sided
> marketplace, where the two parties are told *different things* about the same transition.
>
> **The message is stored rather than composed on read.** A notification is a record of what
> somebody was actually told, and re-rendering an old one through today's wording can make it
> describe a state the booking is no longer in. The cost is accepted and real: a typo fix does not
> reach rows already written, and translating the interface would need this reconsidered.

Indexes: `idx_notifications_user (user_id, created_at DESC)` for the list · **`idx_notifications_unread
(user_id) WHERE read_at IS NULL`** — partial, because the unread count is polled by the header for
every signed-in user for as long as a tab is open, and a partial index stays small permanently
while a full one would grow with every notification ever sent.

## Conventions

- Migrations numbered sequentially, **never edited once applied** — the runner stores an
  LF-normalised SHA-256 and aborts the whole run if one changed.
- Idempotent DDL: `IF NOT EXISTS`, `DROP ... IF EXISTS`, `ON CONFLICT DO NOTHING` on seeds.
- **A list of allowed values that grows with use is a lookup table**, not a `CHECK` — there is no
  `ADD VALUE` for a CHECK, so every change re-declares the whole list, which is how a value gets
  silently dropped. A closed set tied to code may be a `CHECK`.
- **Money is integer paise, always.** A float in a money path is a bug.
- Multi-step writes run in a transaction.
- **Repo-wide search-and-replace must never touch `src/sql/`** — a comment is part of the checksum.
