# 4. Non-functional requirements

Cross-cutting: these apply to **every feature, present and future** — not a per-feature checklist.
Status here is what is actually true today, not the aspiration.

**Key:** ✅ satisfied · 🟡 partial · ⬜ not started

---

## NFR-1 — Authorization is relationship-based, not role-based  🟡

There is no role hierarchy. The question is never "what role is this person?" but **"what is their
relationship to this record?"** — am I this listing's owner, this booking's renter, this review's
subject.

- Written next to the data, in the service layer, never as a route gate.
- The only genuine role is `ADMIN`, for platform staff.

**Today:** the *pattern* is established and `requireAdmin` exists, but no endpoint owns a record yet,
so nothing exercises it. Becomes real at step 3.

## NFR-2 — Registration discloses nothing about who is registered  ✅

The central guarantee of step 1, and the one most easily broken by a well-meaning copy edit.

- Identical status, body and shape for a new, unverified and verified email.
- The password is hashed on **every** path, so timing cannot substitute for the response.
- The difference lives in the **email**, where only the address owner can read it.
- Every verification-token failure answers `410` byte-identically.
- Pinned by tests, including one asserting the "check your inbox" page's copy.

## NFR-3 — Credentials are never recoverable from storage  ✅

- Passwords: bcrypt, cost 10 (4 under test — the suite has no adversary, and bcrypt embeds its cost
  in the hash so verification does not care).
- Tokens: 32 bytes from a CSPRNG, stored as SHA-256 only. A test asserts the raw value is absent
  from the database.
- **A raw token or a link is never logged**, in any path — except deliberately in development, where
  there is no inbox and the alternative is unusable. Production refuses to send rather than falling
  back to logging.

## NFR-4 — Sessions cannot be read by JavaScript  ✅

httpOnly, `SameSite=Strict`, `Secure` in production. So an XSS bug anywhere in the frontend cannot
steal a session — which is the whole reason for a cookie over a header.

`SameSite=Strict` is affordable only because the frontend and API are **same-origin** (Vite proxy in
development, Nginx in production). Split them across domains and this becomes `None`, and CSRF
protection has to be added back by hand.

## NFR-5 — Nothing about identity is trusted from a token  ✅

The JWT carries only a user id — no role, no verification state. Both are read from the database on
every request.

Not caution for its own sake: baked in, verification state would keep saying "unverified" for the
token's full 12-hour life, so someone who just confirmed their email could not act until they signed
out and back in. Suspension would take as long to bite.

## NFR-6 — Every write validates server-side  ✅

Each write has a validator. Unknown keys are **stripped**, not ignored — `role`, `is_admin` and
`status` in a request body never reach a service.

## NFR-7 — Money is never approximate  ⬜

- **Integer paise, always.** A float in a money path is a bug.
- Totals **derived by `SUM`**, never stored — a stored total and its line items drift apart, and the
  drift is invisible.
- Money crosses the API as an integer plus a pre-formatted display string, so no client does money
  arithmetic.
- **The cheapest applicable rate combination**, computed server-side and shown itemised before
  booking. Charging 30 × daily when a monthly rate exists is a 60% overcharge.

**Nothing here is built** — it lands at steps 3 and 6, and is written down now so the first line of
money code starts correct.

## NFR-8 — The same thing cannot be rented twice over  ⬜

The hardest correctness problem in the product. Two people can hit Book on one camera for one
weekend in the same millisecond.

Planned as a **Postgres exclusion constraint over a `tstzrange`**, so overlapping confirmed bookings
are impossible at the database level rather than by an application check that a future code path
might skip. Step 4.

## NFR-9 — Rate limits on unauthenticated endpoints only  ✅

Register, verify, forgot-password and reset-password count **all** requests (a success sends an
email, or is a token guess); login counts **failures only** (a household behind one NAT is one IP).
**Never a global limiter** — it would throttle ordinary browsing.

**Every limiter is keyed on the IP, never on a submitted email address.** A per-address limit would
answer differently for an address that had recently been used, which rebuilds the enumeration oracle
inside the limiter. Per-account throttling lives in the database instead — the reset cooldown — where
it is invisible from outside.

**Known limitation:** in-memory store, so counts are per process and reset on deploy. Correct for a
single instance; a second would need a shared store before the numbers mean anything.

## NFR-10 — Notifications are side effects, never part of the transaction  ✅

The user row and its token commit **before** anything is sent, and the send is fired after the
response and never awaited. A mail outage must not make a signup look like the user's fault.

There is a test that forces the transport to throw and asserts registration still answers `202` with
both records present. It pins a design decision, not a behaviour.

## NFR-11 — Usable on a phone, by someone who has never seen it  🟡

A public marketplace found on mobile data, not an internal tool used all day:

- 16px base type and 48px controls, not a dense 14px/44px.
- No webfonts — a download either blocks first paint or reflows when it lands.
- Status is words plus an indicator, never colour alone.
- Every focus ring from one `:focus-visible` rule.
- **Labels bundled with controls**, so a field cannot ship unnamed to a screen reader.

**Today:** true of everything built. Untested at listing-grid scale.

## NFR-12 — Responsive at real marketplace scale  ⬜

Target: 10,000 listings, 50,000 bookings.

- Every list endpoint paginated — defaulted so a caller who asks for no page still gets a bounded
  one, capped so nobody can request the whole table.
- `total` counted with the **same `WHERE`** as the page, from one shared clause.
- Counts get their own endpoint. Never download a list to derive a number.
- **Pagination without a supporting index is theatre.**

Nothing paginated exists yet — no list endpoint does.

## NFR-13 — No secrets in the repository  ✅

`.gitignore` covers `.env*` with the examples allowed back — deny-all-then-allow, the only form safe
against the next new variant. The server refuses to boot without `JWT_SECRET` or a database, naming
what is missing.

## NFR-14 — The test suite cannot destroy real data  ✅

It `TRUNCATE`s tables, so `testDatabaseGuard` refuses unless `NODE_ENV=test` **and** the resolved
database name ends in `_test`. It **fails closed** — configuration it cannot parse is a refusal. Its
error names the database and never the connection string.

**CI is configured to satisfy the guard, never to bypass it.** A safety check with an "except in CI"
escape hatch is a safety check with a hole in it.

## NFR-15 — The code explains its decisions  ✅

Every file opens with what it is for; every export documents inputs, output and failure modes; every
non-obvious choice says **why**. Comments that restate the code are noise; the ones that survive a
year are the ones recording a decision — and most of these trace to a specific bug in
[troubleshooting.md](troubleshooting.md).
